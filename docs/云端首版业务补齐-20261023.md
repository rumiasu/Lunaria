## 两个实际缺口

1. 原防重以 List/Map 的 toString 拼接内容。预约备注 `quiet, <cardId>` 与备注 `quiet` 加 cardId 可以产生同一指纹；退款 evidence/note 中的 `, note=` 也可混淆。新增两条业务回归在原实现均失败。现用带类型、长度及集合数量的规范编码，Map 按字段名排序，保存 v2 前缀与完整 SHA-256；不同内容返回 409，相同请求仍复用结果。无需改 commands 表。旧购卡等单字符串请求保持兼容；旧多字段指纹丢失了字段边界，明确 409 要求核对原结果，不删除原结果、不换键重复执行。
2. 既有后端只能使用演示顾客，没有店长建档或保存联系方法的入口。现补店长建档、完整资料更新、姓名/编号/联系方法搜索，以及有效卡余次 ≤ 1 的人工联系建议。新档案零本金、零履约、NORMAL / UNDECIDED；编辑只改姓名与联系资料，不改旧卡、余额、等级、资格或微信绑定。同名允许，不合并档案。联系方式/备注仅店长可读，不自动发送消息。

`customer_contacts` 为独立表，V004 仅新增此表。全新 schema 与 V001–V004 在 MySQL 上最终结构一致，14 张 InnoDB 表；旧本金、来源流水与绑定保留。H2 仍用 CREATE TABLE IF NOT EXISTS 增加表，不重建已有业务表。顺带修正此前 V001 表级 CHECK 修复后遗留的旧校验摘要；V001–V003 SQL 本轮未改，CI 现核对 SHA256SUMS。

接口例子与旧操作编号处理见 [API 清单](API清单.md)，业务取舍仍只维护 [首版规则与待定项](首版规则与待定项.md)。联系资料的空字段在完整更新时清空；联系提示包括无有效卡的顾客，供店长人工判断，不构成营销任务。前端暂缓，因此本轮新增入口先通过后端 API 使用。
