# AI 先交付，你之后再读

无需先写代码才能推进。先运行演示，按“林女士购买面护五次卡 → 店长确认预约 → 服务后核销 → 退卡试算”理解业务，再沿一条数据流阅读。

## 从一次购卡追到数据库

1. `miniapp-customer/pages/home/index.wxml`：找到“余额购卡”按钮，`bindtap="purchase"` 连接脚本函数。
2. 同目录 `index.js` 的 `purchase`：显示价格和规则，确认后 POST `/me/purchases`；前端只提交套餐编号，不决定实际扣款价。
3. `miniapp-shared/api.js` 的 `mutate`：保存请求操作编号。断网后用原按钮重试保持相同编号，避免“没收到响应”变成第二次扣款。
4. `backend/src/main/java/cn/lunaria/ApiController.java` 的 `purchase`：身份来自已登录会话，`Principal` 不是顾客自己填的 customerId；校验请求后交给应用服务。
5. `ShopService.purchase`：`@Transactional` 让扣余额、生成卡、流水和操作结果要么一起成功，要么全部回滚。实际价从套餐及该等级专属价格读取，卡保存权益快照。
6. `ShopService.command`：先锁店铺行，再查询 `commands`；同编号同内容回原结果，同编号不同内容拒绝。
7. `StoreMapper.balance / insertCard / insertEntry / commandSave`：看到带 `#{}` 绑定参数的 SQL。不要把外部输入拼接为 SQL。
8. `backend/src/main/resources/schema.sql`：依次看 customers、packages、tier_prices、cards、ledger、commands；原价/套餐价/本次实付不是一回事。
9. `BusinessFlowTest`：先读 `purchaseIsAtomicIdempotentAndSnapshotProtected`，再读 `failureBetweenDeductAndIssueRollsBackBoth`、并发重试、95 元用两次退 57 元和权限隔离测试。测试证明边界，不能代替微信真机/MySQL验收。

## 再看两条线

预约：`booking/index.js → ShopService.book → confirm → capacity`。提交待确认，确认才占容量；峰值并发用时间事件扫描，不能只数所有相交预约。

核销与退款：`complete → SERVICE` 按分摊价值确认履约；`reverse → REVERSAL` 追原流水；`requestRefund → REVIEW → reviewRefund → REFUND_TO_BALANCE` 追到单卡和申请。余额购卡退款不重复付现金，储值退款预留不等于已付款。

## 不急着学的部分

微信授权、支付回调、通知、正式部署和最终美术在待定清单；当前没有假装开通。先看懂身份、事务、快照、来源流水四件事，再扩技术细节。
